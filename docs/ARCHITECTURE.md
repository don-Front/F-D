# Архитектура проекта

Документ описывает устройство `portfolio-starter` и правила, по которым его нужно расширять.
Цель — чтобы новый разработчик (или вы через год) мог открыть репозиторий и сразу понять, куда класть код.

## Обзор

Это универсальный React + Vite starter template без бизнес-логики, роутинга и лишних зависимостей.
Стек: React 19, Vite, JavaScript, SCSS Modules, ESLint, Prettier, EditorConfig, npm.

Alias `@` указывает на `src/`. Пример:

```js
import Button from '@/components/ui/Button';
```

## Структура `src/`

```text
src/
  assets/        — статические ресурсы
  components/    — переиспользуемые компоненты
  constants/     — общие константы приложения
  data/          — временные/статические данные
  hooks/         — переиспользуемые React-хуки
  layouts/       — композиции страниц (header/footer/shell)
  lib/           — конфигурация сторонних библиотек
  pages/         — страницы приложения
  services/      — работа с API и внешними источниками данных
  styles/        — глобальные стили
  utils/         — чистые вспомогательные функции
  App.jsx        — корневой компонент
  main.jsx       — точка входа
```

### Назначение папок

| Папка                | Назначение                                                                 |
| -------------------- | -------------------------------------------------------------------------- |
| `assets/`            | Шрифты, иконки, изображения и прочие статические файлы                     |
| `components/common/` | Общие компоненты без узкой UI-роли (например, ErrorBoundary)               |
| `components/layout/` | Компоненты раскладки (`Container` и подобные)                              |
| `components/ui/`     | Базовые UI-примитивы (`Button`, `Title`, `Section`)                        |
| `constants/`         | Routes, breakpoints, navigation, storage keys и другие стабильные значения |
| `data/`              | Моки и статический контент до появления API                                |
| `hooks/`             | Переиспользуемые хуки без привязки к конкретной странице                   |
| `layouts/`           | Каркасы страниц: общая оболочка, зоны header/main/footer                   |
| `lib/`               | Настройка axios, swiper, gsap и других внешних библиотек                   |
| `pages/`             | Страницы/экраны приложения                                                 |
| `services/`          | HTTP-запросы, адаптеры API, клиентские интеграции                          |
| `styles/`            | Reset, CSS-переменные, типографика, глобальные стили                       |
| `utils/`             | Чистые функции без React и без побочных эффектов                           |

## Правила создания компонентов

1. Один компонент — одна ответственность.
2. Для каждого компонента создавайте папку:

```text
ComponentName/
  ComponentName.jsx
  ComponentName.module.scss
  index.js
```

3. Экспортируйте компонент через `index.js`:

```js
export { default } from './ComponentName';
```

4. Используйте functional components и hooks.
5. Не смешивайте UI-примитивы и страничную логику: страница собирает компоненты, компонент не знает о роуте.
6. Предпочитайте семантические HTML-теги (`button`, `section`, `main`, `h1`–`h6`) вместо лишних `div`.

### Где какой компонент класть

- `components/ui/` — атомарные элементы интерфейса
- `components/layout/` — структура и ограничения ширины/отступов
- `components/common/` — переиспользуемые блоки, которые не являются ни ui-, ни layout-примитивом
- `pages/` — экраны, собранные из компонентов
- `layouts/` — общая оболочка для нескольких страниц

## Правила создания страниц

1. Страница живёт в `src/pages/`.
2. Имя папки/файла отражает экран: `Home`, `About`, `ProjectDetails`.
3. Страница отвечает за сборку экрана, а не за низкоуровневый UI.
4. Запросы к API вызывайте через `services/`, а не прямо из JSX-разметки без слоя сервиса.
5. Пока роутинг не подключён, не добавляйте его «на будущее». Подключайте, когда реально понадобится.

## Правила использования hooks

1. Хуки кладите в `src/hooks/`.
2. Имя начинается с `use`: `useMediaQuery`, `useLocalStorage`.
3. Хук должен быть переиспользуемым. Логику одного конкретного экрана лучше оставить рядом со страницей, пока она не понадобится повторно.
4. Не смешивайте в одном хуке сетевые вызовы, DOM-эффекты и бизнес-правила без необходимости — разделяйте ответственность.

## Правила использования services

1. Всё взаимодействие с API — через `src/services/`.
2. Сервис возвращает данные/ошибки в удобном для UI виде.
3. Не храните JSX в сервисах.
4. Базовый HTTP-клиент (если появится axios/fetch-обёртка) настраивайте в `lib/`, а эндпоинты описывайте в `services/`.

## Правила использования lib

1. `lib/` — только для конфигурации и тонких обёрток над сторонними библиотеками.
2. Не устанавливайте библиотеки заранее «про запас».
3. Файл в `lib/` появляется вместе с реальной зависимостью.
4. Компоненты импортируют готовую конфигурацию из `lib/`, а не дублируют setup у себя.

## Правила использования constants

1. Константы — это стабильные значения без побочных эффектов.
2. Типичные файлы: `routes.js`, `breakpoints.js`, `navigation.js`, `storageKeys.js`.
3. Не кладите в `constants/` моки страниц — для этого есть `data/`.
4. Не кладите сюда функции с логикой — для этого есть `utils/` или `services/`.

## Правила использования data

1. Используйте `data/` для временных данных и моков.
2. Когда появится API, замените импорт из `data/` на вызов `services/`.
3. Не превращайте `data/` в постоянное хранилище бизнес-логики.

## Правила использования styles

### Глобальные стили (`src/styles/`)

- `reset.scss` — сброс браузерных стилей
- `variables.scss` — CSS-переменные (цвета, отступы, типографика, радиусы)
- `typography.scss` — базовые текстовые стили
- `globals.scss` — точка сборки глобальных стилей, подключается в `main.jsx`

Глобально держите только то, что действительно глобально.
Стили конкретного компонента не должны попадать в `styles/`.

### Component.module.scss

Используйте CSS Modules для стилей компонента:

```text
Button/
  Button.jsx
  Button.module.scss
```

```js
import styles from './Button.module.scss';
```

Когда нужен module:

- стили принадлежат одному компоненту
- нужно избежать конфликтов имён классов
- стили не должны протекать наружу

Когда module не нужен:

- глобальный reset/variables/typography
- стили сторонней библиотеки, подключаемые один раз

## Соглашения по именованию

| Тип                          | Правило                          | Пример                       |
| ---------------------------- | -------------------------------- | ---------------------------- |
| Компонент / папка компонента | `PascalCase`                     | `Button`, `PageHeader`       |
| Файл компонента              | `PascalCase.jsx`                 | `Button.jsx`                 |
| Стили компонента             | `PascalCase.module.scss`         | `Button.module.scss`         |
| Хук                          | `camelCase`, начинается с `use`  | `useMediaQuery.js`           |
| Утилита / сервис / константы | `camelCase`                      | `formatDate.js`, `routes.js` |
| Папки-слои                   | `camelCase` / короткое имя слоя  | `components`, `hooks`, `lib` |
| CSS-переменные               | `--kebab-case`                   | `--color-text`               |
| Env-переменные               | `VITE_` + `SCREAMING_SNAKE_CASE` | `VITE_API_URL`               |

## Импорты через `@`

Всегда предпочитайте alias `@` для импортов из `src/`:

```js
import Button from '@/components/ui/Button';
import { ROUTES } from '@/constants/routes';
import { formatDate } from '@/utils/formatDate';
```

Относительные импорты (`./`, `../`) оставляйте только для соседних локальных файлов внутри одной папки модуля.

### Порядок импортов

ESLint проверяет порядок автоматически:

1. React
2. Внешние библиотеки
3. Services
4. Hooks
5. Lib
6. Constants
7. Utils
8. Components
9. Styles
10. Локальные файлы

## Переменные окружения

Пример лежит в `.env.example`.
Реальные значения храните в `.env` (файл в git не коммитится).

В коде Vite доступны только переменные с префиксом `VITE_`:

```js
const apiUrl = import.meta.env.VITE_API_URL;
```

## Масштабирование проекта

Рекомендуемый порядок роста:

1. Начните с `components/ui` + `pages`.
2. Вынесите повторяющуюся логику в `hooks` и `utils`.
3. При появлении API добавьте `services` и при необходимости клиент в `lib`.
4. Стабильные значения вынесите в `constants`.
5. Когда появятся общие оболочки страниц — используйте `layouts`.
6. Роутинг, state-manager и UI-kit сторонних библиотек подключайте только по реальной потребности.

Чего избегать:

- преждевременных абстракций
- установки библиотек «на будущее»
- хранения бизнес-логики в UI-компонентах
- глобальных стилей для локальных компонентов
- дублирования одних и тех же конфигов в разных местах
